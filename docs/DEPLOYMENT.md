# RelayNorth: Final Web Deployment and Operations Guide

This is the deployment and runtime reference for RelayNorth.

It answers two questions:

1. How do we deploy the public site, admin console, API, PostgreSQL, and Redis on the web?
2. What happens after a visitor submits a URL, and how does that compare with a Proxyium-style browser proxy?

The implementation was reviewed end to end against the current repository. Public Proxyium-style descriptions were used only to compare the user experience and request model: a visitor enters a URL, chooses or is assigned a relay location, the service fetches the destination, and the browser continues through the relay. See [Proxyium's overview of browser proxies](https://proxyium.com.in/how-does-a-web-proxy-work/) and [Proxyium's public product description](https://proxyium.in/).

RelayNorth follows that browser-only model, but it is intentionally safer and narrower than an unrestricted public proxy:

- destinations must be on `ALLOWED_PROXY_ORIGINS`;
- private, loopback, metadata, credential-bearing, and unapproved destinations are rejected;
- sessions are short-lived and signed;
- a session is pinned to one logical relay cell;
- only `GET` and `application/x-www-form-urlencoded` `POST` are supported;
- the browser page is rewritten back through the RelayNorth session;
- the service does not create a device-wide VPN and does not proxy arbitrary internet traffic.

## 1. What is deployed

RelayNorth is one FastAPI application that serves both user-facing applications and the control plane.

| Component | Repository location | Runtime responsibility |
|---|---|---|
| Public site | `public/` | Landing page, browse shell, FAQ, legal pages, status page, and blog pages |
| Public browser client | `public/app.js`, `public/browse.html` | Creates sessions, opens the relay tab, polls status, and embeds the proxied page |
| Admin console | `admin/` → `admin/dist/` | React/Vite control room for blog, regions, abuse, usage, and audit events |
| FastAPI control plane | `backend/app/main.py` | HTML delivery, API, session lifecycle, admin auth, and proxy response handling |
| Proxy implementation | `backend/app/proxy.py` | URL validation, upstream fetch, cookie handling, redirects, and HTML rewriting |
| Regional worker | `worker/main.py` | Authenticated outbound fetch from a regional network |
| Durable database | PostgreSQL | Users, roles, regions, sessions, blog, reports, audits, and usage aggregates |
| Coordination store | Redis | Distributed rate limits, concurrency, and per-client bandwidth counters |

The app resolves `public/` and `admin/dist/` relative to the repository root. A deployment artifact must preserve this layout:

```text
repository/
├── backend/
├── public/
├── admin/
│   └── dist/          # generated by npm --prefix admin run build
├── alembic/
├── alembic.ini
├── requirements.txt
└── .env               # injected by the deployment platform; never committed
```

## 2. Current production reality

The application is production-shaped, but the current repository is still a controlled vertical slice. These facts must be understood before deployment:

### Implemented now

- Browser-only relay experience.
- Public site and React admin served from one origin.
- Allowlisted HTTP(S) destinations.
- Signed session tokens and eight-hour signed admin cookies.
- Session expiry, request limits, concurrency limits, rate limits, and a 100 MB cumulative egress cap per observed client IP.
- Logical relay cells: Europe, United States, and Asia.
- Egress IP displayed to the user and returned by the session API.
- Postgres persistence and Redis coordination when configured.
- In-memory fallback when those services are unavailable.
- Sanitized Markdown blog publishing, audit events, abuse reports, and operator telemetry.

### Not yet equivalent to a large commercial proxy network

- The regional worker service is implemented, but it must be deployed separately in EU, US, and Asia and supplied with real provider-routed egress addresses.
- The checked-in egress addresses (`203.0.113.x`) are documentation/test addresses, not public internet egress IPs.
- The repository includes one-worker-per-region Compose wiring; a production pool still requires real regional hosts/IPs and lease management.
- HTML attributes are rewritten for the supported subset; arbitrary JavaScript-heavy applications, WebSockets, streaming, downloads, and every browser API are not guaranteed to work.
- There is no CONNECT tunnel and no unrestricted forward-proxy mode.

Do not market the current deployment as a global anonymous proxy until regional workers, real egress IP assignment, abuse operations, capacity controls, and the broader rewriting model have been implemented and reviewed.

## 3. User experience and request flow

The intended user flow is:

```text
Visitor opens /
      │
      ├─ enters an approved URL and selects a relay cell
      │
      ├─ browser POSTs /api/v1/sessions
      │       │
      │       ├─ validate scheme, host, port, IP, credentials, and allowlist
      │       ├─ check session-create rate limit
      │       ├─ pin session to the selected cell
      │       └─ return signed token, expiry, browse URL, and displayed egress IP
      │
      ├─ opens /browse?session=...&token=...&url=... in a new tab
      │
      ├─ browse shell GETs /api/v1/sessions/{id}/status
      │
      └─ iframe requests /api/v1/proxy/{id}?token=...&url=...
              │
              ├─ verify signed token and session/cell binding
              ├─ verify the pinned cell is accepting traffic
              ├─ enforce client-IP, session, rate, concurrency, and bandwidth limits
              ├─ fetch the allowlisted destination from the server
              ├─ preserve the session cookie jar
              ├─ rewrite supported HTML links/forms/assets through the relay
              └─ return the upstream status, content type, and bounded body
```

### Session creation

`POST /api/v1/sessions` accepts:

```json
{"region":"eu","url":"https://allowed.example/"}
```

The response includes:

- `session_id` — opaque session identifier;
- `cell_id` and `region` — the pinned logical cell;
- `egress_ip` — the cell's configured displayed egress address;
- `expires_at` — normally 15 minutes from creation;
- `session_token` — signed token containing session, cell, and expiry claims;
- `browse_url` — the user-facing relay shell URL.

The initial URL establishes the session origin. Later proxy requests are required to remain on that origin, including redirects.

### Proxy behavior

The proxy accepts `GET` and `POST` only. For `POST`, the content type must be `application/x-www-form-urlencoded` and the body must be no larger than the configured form limit.

For HTML responses, RelayNorth rewrites supported `href`, `src`, and `action` attributes back to `/api/v1/proxy/{session_id}`. Redirect locations are validated against the pinned session origin before being returned. Upstream cookies are stored in the session cookie jar and reused for later requests.

The proxy currently uses a 12-second upstream timeout and rejects response bodies over 2 MB. These limits protect the control plane and are not a guarantee that every modern web application will render.

## 4. Deployment topology

### Recommended production topology

```text
Internet
   │ HTTPS
   ▼
CDN / WAF / Load balancer
   │ forwards Host, X-Forwarded-For, X-Forwarded-Proto
   ▼
RelayNorth application replicas
   │                    │
   ▼                    ▼
PostgreSQL          Redis
```

Use one application service initially. Add replicas only after PostgreSQL and Redis are healthy and shared by every replica.

### Why Postgres and Redis are required for scale

Without external stores, each worker has its own memory state. A session created on worker A may not exist on worker B, and every worker has a separate copy of rate, concurrency, and bandwidth state. With Postgres and Redis configured, sessions and durable content can be shared and coordination can be distributed.

The in-memory mode is appropriate for local development, a single-worker demo, or emergency degraded service. It is not the correct topology for a multi-worker public relay.

## 5. Configuration

Set these values in the deployment platform's secret/environment configuration. Do not commit a production `.env` file.

| Variable | Required production value |
|---|---|
| `APP_ENV` | `production` — enables the `Secure` admin cookie |
| `SECRET_KEY` | Long, random, private signing key. Rotation invalidates active session/admin tokens. |
| `ADMIN_EMAIL` | Real operator email |
| `ADMIN_PASSWORD` | Strong bootstrap password; change it before exposing the admin console |
| `DATABASE_URL` | `postgresql+psycopg://USER:PASSWORD@HOST:5432/DB` |
| `REDIS_URL` | `redis://HOST:6379/0` or a TLS Redis URL supplied by the provider |
| `ALLOWED_PROXY_ORIGINS` | Comma-separated, reviewed HTTPS origins; never `*` |
| `ALLOW_LOCAL_TEST_ORIGIN` | `false` |
| `REQUIRE_REGIONAL_WORKERS` | `true` in production; refuses direct-fetch fallback |
| `WORKER_SHARED_SECRET` | Long secret shared only between control plane and workers |
| `RELAY_WORKER_EU_URL` | Private URL of the EU worker |
| `RELAY_WORKER_US_URL` | Private URL of the US worker |
| `RELAY_WORKER_APAC_URL` | Private URL of the Asia worker |
| `RELAY_EGRESS_IP_EU` | Verified public egress address of the EU worker |
| `RELAY_EGRESS_IP_US` | Verified public egress address of the US worker |
| `RELAY_EGRESS_IP_APAC` | Verified public egress address of the Asia worker |

Example production configuration:

```dotenv
APP_ENV=production
SECRET_KEY=<generated-random-secret>
ADMIN_EMAIL=ops@example.com
ADMIN_PASSWORD=<generated-bootstrap-password>
ALLOWED_PROXY_ORIGINS=https://docs.example.com,https://status.example.com
ALLOW_LOCAL_TEST_ORIGIN=false
REQUIRE_REGIONAL_WORKERS=true
WORKER_SHARED_SECRET=<worker-only-secret>
RELAY_WORKER_EU_URL=http://eu-worker.internal:8000
RELAY_WORKER_US_URL=http://us-worker.internal:8000
RELAY_WORKER_APAC_URL=http://apac-worker.internal:8000
RELAY_EGRESS_IP_EU=<verified-eu-public-ip>
RELAY_EGRESS_IP_US=<verified-us-public-ip>
RELAY_EGRESS_IP_APAC=<verified-asia-public-ip>
DATABASE_URL=postgresql+psycopg://relaynorth:<password>@postgres.internal:5432/relaynorth
REDIS_URL=redis://redis.internal:6379/0
```

### Fixed application limits

The following are currently code settings in `backend/app/config.py`, not environment variables:

| Limit | Current value |
|---|---:|
| Session lifetime | 900 seconds |
| Maximum response | 2,000,000 bytes |
| Session request limit | 120 |
| Session creation rate | 10 per client IP per 60 seconds |
| Proxy request rate | 60 per client IP/session per 60 seconds |
| Concurrent requests | 2 per session |
| Cumulative egress | 100 MB per client IP |

Change these through a reviewed code change and redeploy. Do not silently increase them to compensate for an under-sized service.

## 6. Build and release

### Local or CI build

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

npm --prefix admin ci
npm --prefix admin run build

python -m compileall -q backend/app
python -m pytest -q
```

The public site is vanilla HTML/CSS/JavaScript and has no separate bundler. The admin console is the only frontend build and must produce `admin/dist/` before the application image is assembled.

The repository includes a multi-stage [`Dockerfile`](../Dockerfile). It builds `admin/dist/` and produces one image that can run either the control plane (`backend.app.main:app`) or a regional worker (`worker.main:app`) by overriding the container command.

```bash
docker build -t relaynorth:release .
docker compose config
```

### Database release step

With production environment variables loaded:

```bash
alembic upgrade head
```

The application also calls its initialization path at startup. Keep migrations in the release process anyway so schema changes are explicit, reviewable, and repeatable.

### Artifact validation

Before publishing an image or bundle, confirm it contains:

```bash
test -f backend/app/main.py
test -f public/index.html
test -f admin/dist/index.html
test -f admin/dist/assets/app.js || test -f admin/dist/app.js
test -f alembic/versions/0001_initial_schema.py
```

## 7. Deployment options

### Option A: VM or managed container service

1. Build the Python environment and `admin/dist/` in CI.
2. Copy the repository layout into the image or release bundle.
3. Inject production environment variables.
4. Run migrations.
5. Start the app on an internal port.
6. Put a TLS reverse proxy or load balancer in front.
7. Configure liveness, readiness, logs, backups, and alerts.

Recommended start command for one worker:

```bash
uvicorn backend.app.main:app \
  --host 0.0.0.0 \
  --port 8000 \
  --proxy-headers \
  --forwarded-allow-ips="<trusted-load-balancer-address>"
```

For multiple workers, use shared Postgres and Redis:

```bash
gunicorn backend.app.main:app \
  -k uvicorn.workers.UvicornWorker \
  -w 4 \
  --bind 0.0.0.0:8000 \
  --forwarded-allow-ips="<trusted-load-balancer-address>" \
  --timeout 30
```

### Option B: Railway or similar PaaS

Use the existing [`API_AND_RAILWAY_DEPLOYMENT.md`](./API_AND_RAILWAY_DEPLOYMENT.md) for the provider-specific setup. The same application rules still apply:

- build `admin/dist/` during the image build;
- provision Postgres and Redis for more than one worker;
- set the allowlist and disable the local test origin;
- use a trusted forwarded-IP configuration;
- do not describe logical cells as real regional egress until regional workers exist.

### Option C: Docker Compose

The repository's `docker-compose.yml` now starts a control plane, EU worker, US worker, Asia worker, PostgreSQL, and Redis. It is a local wiring test and uses reserved documentation IPs; it is not proof of real regional egress. For production, deploy each worker in the intended region and replace the worker URLs, shared secret, and egress IP metadata with private endpoints and verified public addresses.

## 8. Reverse proxy and TLS

The public hostname must terminate HTTPS. The reverse proxy must forward the original host, scheme, and client address:

```nginx
server {
    listen 443 ssl http2;
    server_name relay.example.com;

    ssl_certificate     /etc/ssl/relay/fullchain.pem;
    ssl_certificate_key /etc/ssl/relay/privkey.pem;

    client_max_body_size 4m;
    proxy_read_timeout 30s;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Redirect port 80 to HTTPS. Configure the application with `--proxy-headers` and a precise `--forwarded-allow-ips` value. The application uses the observed client IP for session binding, rate limits, and the 100 MB bandwidth cap. If forwarded headers are accepted from untrusted networks, a client can spoof its identity or all traffic can collapse into the load balancer's IP.

## 9. Health, readiness, and operations

`GET /healthz` always returns HTTP 200 so the process can be monitored for liveness. The response reports whether durable dependencies are healthy:

```json
{
  "ok": true,
  "degraded": false,
  "service": "relaynorth-control-plane",
  "dependencies": {
    "ok": true,
    "mode": "postgresql+redis"
  }
}
```

Use two checks:

- **Liveness:** HTTP 200 means the process is alive.
- **Readiness:** require `degraded == false` for a normal production relay. A degraded service is serving from memory and may lose state on restart.

Authenticated operator endpoints provide:

- `GET /api/v1/admin/usage` — active sessions, requests, egress bytes, blocked requests, and cell states;
- `GET /api/v1/admin/audit-events` — admin actions;
- `GET /api/v1/admin/abuse-reports` — abuse queue;
- `GET /api/v1/admin/regions` — cell health and capacity.

Ship application stdout/stderr to the platform log system and alert on:

- `degraded: true`;
- repeated 429, 403, 502, or 503 responses;
- upstream timeout growth;
- high active sessions or egress usage;
- Redis/Postgres connectivity failures;
- abuse-report backlog.

## 10. Security and abuse controls

Before exposing the hostname, verify all of the following:

- [ ] `APP_ENV=production`.
- [ ] `SECRET_KEY` is random and not present in Git, logs, or the image.
- [ ] Default admin credentials are replaced.
- [ ] `ALLOW_LOCAL_TEST_ORIGIN=false`.
- [ ] `ALLOWED_PROXY_ORIGINS` contains only reviewed HTTPS origins.
- [ ] `ALLOWED_PROXY_ORIGINS` is never `*`.
- [ ] PostgreSQL and Redis are private-network services.
- [ ] The proxy trusts forwarded headers only from the load balancer.
- [ ] TLS is enforced at the edge.
- [ ] Admin access is protected by network policy, SSO, VPN, or an equivalent control appropriate to the deployment.
- [ ] Abuse reports are reviewed and acted upon.
- [ ] Destination owners and legal/compliance requirements are documented before adding origins.
- [ ] No CONNECT, arbitrary ports, unrestricted POST, or metadata access has been enabled.

The allowlist is the primary product boundary. Adding an origin is an operational and security decision, not merely a configuration convenience.

## 11. Data, persistence, and recovery

Back up PostgreSQL using the managed provider or a scheduled `pg_dump`. The important durable records are:

- admin users and roles;
- published and draft blog content;
- blog revisions;
- abuse reports;
- audit events;
- usage aggregates.

Redis stores coordination and rate/bandwidth state. It can be rebuilt, but a Redis outage should be treated as a readiness incident because limits and cross-worker coordination are no longer reliable.

Sessions are intentionally short-lived. Do not treat session rows or cookie jars as long-term user data.

## 12. Post-deploy acceptance test

Run this against the public hostname after every deployment. Replace the allowlisted URL and admin secret with deployment-specific values.

```bash
BASE=https://relay.example.com

# Liveness and dependency state
curl -fsS "$BASE/healthz" | jq '{ok, degraded, mode: .dependencies.mode}'

# Public site and admin shell
curl -fsS -o /dev/null -w 'public %{http_code}\n' "$BASE/"
curl -fsS -o /dev/null -w 'admin  %{http_code}\n' "$BASE/admin/"

# Allowlisted session: expect 200 and region/egress_ip
SESSION=$(curl -fsS -X POST "$BASE/api/v1/sessions" \
  -H 'content-type: application/json' \
  -d '{"region":"eu","url":"https://<allowlisted-origin>/"}')
echo "$SESSION" | jq '{session_id, region, egress_ip, expires_at, browse_url}'

# Non-allowlisted destination: expect 403
curl -sS -o /dev/null -w 'blocked %{http_code}\n' \
  -X POST "$BASE/api/v1/sessions" \
  -H 'content-type: application/json' \
  -d '{"region":"eu","url":"https://example.com/"}'

# Admin login: expect 200 and a relay_admin cookie
curl -i -X POST "$BASE/api/v1/admin/auth/login" \
  -H 'content-type: application/json' \
  -d '{"email":"<admin-email>","password":"<admin-password>"}' \
  | grep -iE 'HTTP/|set-cookie'
```

Expected results:

- `/healthz` is 200 and `degraded` is false;
- public and admin shells are 200;
- the allowlisted session includes a region, egress address, expiry, and browse URL;
- an unapproved origin is 403;
- admin login is 200 and sets an HttpOnly `relay_admin` cookie;
- a browser can open the browse shell, see the target URL and relay IP, and load the allowlisted page inside the relay frame.

## 13. Upgrade and rollback procedure

1. Review the code and migration diff.
2. Build the admin console and application artifact in CI.
3. Run the full test suite.
4. Run `alembic upgrade head` against a staging database.
5. Deploy the new application artifact.
6. Run the acceptance test in §12.
7. Monitor health, dependency state, error rates, usage, and abuse reports.

For rollback, redeploy the previous application artifact. Do not automatically downgrade a production database. If a future migration is destructive, prepare and test a backward-compatible migration or a documented recovery plan before rollout.

## 14. Regional workers and egress routing

### 14.1 What happens today

If `RELAY_WORKER_EU_URL`, `RELAY_WORKER_US_URL`, or `RELAY_WORKER_APAC_URL` is configured, the control plane assigns the session to that worker and sends the outbound fetch to `/internal/v1/fetch`. The worker performs the `httpx` request from its own network and returns a bounded response to the control plane for rewriting and delivery to the browser. If worker URLs are not configured, development mode falls back to direct control-plane fetching. Set `REQUIRE_REGIONAL_WORKERS=true` in production so that fallback is refused.

The checked-in `203.0.113.x` addresses remain documentation/test values. They must be replaced with addresses verified from the actual worker networks.

### 14.2 Target production flow

The production design should separate the public control plane from regional relay workers:

```text
Browser
   │ HTTPS: public session/proxy URL
   ▼
Control plane
FastAPI + Postgres + Redis
   │ 1. validate URL
   │ 2. acquire region/IP lease
   │ 3. send authenticated fetch request
   ▼
Selected regional worker
   ├── EU worker pool ── NAT/public EU IPs
   ├── US worker pool ── NAT/public US IPs
   └── Asia worker pool ── NAT/public Asia IPs
          │
          ▼
     Destination origin
```

The browser must continue to use the public control-plane URL. It must never receive a worker hostname, private worker address, lease key, or internal credential.

### 14.3 How a region selection becomes a real source IP

Selecting `eu`, `us`, or `asia` is only a data value until the selected worker has a network path in that region. The worker must use one of these supported egress designs:

1. **One public IP per worker (recommended first release).** Deploy EU, US, and Asia workers on hosts in those regions. Each host has one stable public outbound address. The session is pinned to one worker for its full lifetime.
2. **Multiple public IPs on one regional host.** Assign several addresses to the host and bind the outbound socket to the leased source address, or configure source-based SNAT rules. The operating system and provider must explicitly support this.
3. **Managed regional egress gateway.** The worker calls a provider that guarantees an exit region and returns the assigned address. Verify the provider's acceptable-use policy, stability, bandwidth, and address ownership.

The application cannot make an upstream request regional by setting an HTTP header. The destination sees the public address selected by the worker's routing/NAT layer.

For the first production version, use one worker and one stable public IP per region. Add a ten-IP pool only after lease accounting, health checks, and abuse controls have been proven.

### 14.4 Session assignment and IP pinning

When `POST /api/v1/sessions` receives `{ "region": "eu", ... }`, the control plane should:

1. Validate the destination and requested region.
2. Query healthy workers and available IP leases for that region.
3. Acquire an atomic Redis lease, for example `relay:lease:eu:eu-01`.
4. Persist `session_id`, `region`, `worker_id`, `egress_ip_id`, and lease expiry in PostgreSQL.
5. Return the session token and browse URL to the browser.
6. Route every proxy fetch for that session to the same worker and egress IP.
7. Release the lease after expiry or an explicit session close.

Do not silently move a session from EU to US if EU is full. Return `503 Selected relay region is busy` and let the user choose another region. Changing the source IP during a session can invalidate destination cookies and make the destination see a new client.

Recommended initial timings:

```text
session TTL:          15 minutes
IP lease TTL:         session TTL + 60 seconds
worker heartbeat:     every 15 seconds
worker unhealthy:     45 seconds without a heartbeat
draining worker/IP:   no new sessions; existing sessions may finish
unavailable worker:   no new sessions; existing sessions fail safely
```

### 14.5 Worker API and trust boundary

Workers should expose only a private, authenticated internal API. They must not be public open proxies.

```http
POST /internal/v1/heartbeat
POST /internal/v1/fetch
GET  /internal/v1/egress-check
```

The control plane sends an approved target URL, method, bounded headers, body, session identifier, and policy claims. The worker returns a bounded status, headers, and body. Worker requests should use mTLS or short-lived signed service tokens and private networking where available.

The worker must repeat the safety checks rather than trusting the control plane blindly:

- HTTP(S) only;
- no credentials in URLs;
- no private, loopback, link-local, multicast, or cloud-metadata destinations;
- only approved origins and ports;
- redirect revalidation;
- maximum request/response sizes;
- GET and approved form POST only;
- session, IP, rate, concurrency, and bandwidth limits;
- no forwarding of client authorization or proxy headers.

### 14.6 Worker health and draining

The worker sends a heartbeat containing its identity, region, capacity, and health. The control plane marks it ready only after an egress check reaches an endpoint owned by the operator and observes the expected public source address.

When an operator drains a worker:

1. Mark it `draining` in the control plane.
2. Stop assigning new sessions to it.
3. Allow existing sessions to finish until their TTL expires.
4. Mark it `unavailable` if it stops responding.
5. Release expired leases with a TTL-based sweeper.

Do not reassign an active session to a different source IP automatically unless the product explicitly accepts cookie and identity changes.

### 14.7 Data model for real regional routing

The current `RegionModel.egress_ip_pool` JSON field is descriptive metadata. A production worker system should add individually tracked records similar to:

| Record | Required fields |
|---|---|
| `relay_workers` | `id`, `region`, private endpoint, credential ID, status, heartbeat |
| `relay_egress_ips` | `id`, `worker_id`, `region`, public address, status, load |
| `relay_ip_leases` | `session_id`, `egress_ip_id`, leased time, expiry |
| `relay_sessions` | `session_id`, `region`, `worker_id`, `egress_ip_id` |

Public `/api/v1/regions` should return region labels, readiness, and approximate capacity only. It should not expose internal worker endpoints, lease keys, or the full public IP inventory.

### 14.8 Regional acceptance test

Before claiming that a region works, use an endpoint owned by the operator that records the source address. For each region:

```text
requested region == assigned region
assigned worker belongs to that region
observed source IP belongs to that region's pool
the same session keeps the same source IP
two sessions can receive two free IPs
an exhausted pool returns 503 rather than silently changing region
```

This test must run from the worker, not from the browser and not from the Railway control-plane process.

## 15. Roadmap to a true Proxyium-style regional network

The current app provides the user experience and control-plane foundation. The next production phase should add:

1. **Regional workers** — deploy proxy workers independently in each target region.
2. **Real egress pools** — assign public IPs that are actually routed from each region; replace the TEST-NET placeholder values.
3. **Worker assignment** — select a worker/IP lease when a session is created and keep that assignment stable until expiry.
4. **Worker-to-control-plane authentication** — use mTLS or signed service credentials; never expose an internal worker API publicly.
5. **Distributed session metadata** — store worker, egress IP, lease expiry, and health state durably.
6. **Capacity and draining** — stop new sessions before taking a worker out of service; allow existing sessions to expire or migrate according to policy.
7. **Broader web compatibility** — carefully add support for CSS URLs, script/API requests, WebSockets, downloads, and streaming only after each path has security and abuse controls.
8. **Abuse prevention** — per-account/IP quotas, destination-level controls, automated abuse signals, and an operator response process.
9. **Privacy policy and retention** — document what request metadata is retained, for how long, and who can access it.
10. **Load and security testing** — test SSRF, DNS rebinding, redirect chains, cookie isolation, tenant/session separation, origin escapes, and regional failure.

Until these are complete, the honest product description is: **a controlled, allowlisted, browser-tab relay with logical region selection** — not a whole-device VPN, not an unrestricted public proxy, and not yet a multi-region egress network.
